# Factory2 data model

This replaces the vocabulary table in
`dev/factory-sim/RULES-FOR-A-WELL-INSTRUMENTED-SOFTWARE-FACTORY.md`; the rules
there still hold, and this is what makes them checkable. It is the data model
only: how events reach the log, and who reads it, come later.

## The idea

**The factory is a set of state machines, an event is a move, and the log is
a path through them.**

- Every entity (an issue, an agent, CI on one push, a release) is an instance
  of a declared machine with named states and allowed edges. The world is the
  current state of every instance plus the few facts that are not states:
  dependencies, which pull request belongs to which issue, builds.
- An event is accepted only if it is a legal move: right shape, right actor,
  and every state change it causes lies along a declared edge.
- Every state change closes one interval and opens the next. The time every
  item spent in every state (rule 9), waiting included (rule 10), falls out
  of checking the log; no actor logs it.

The checker (`factory/world.py`), the simulation and the measurements are
three readers of the same machines: the simulation picks among the legal next
moves, the checker refuses the others, and measurement reads the intervals.

## Principles

1. **The code is the schema.** Shapes are in `model.py`, machines in
   `machines.py`, legality in `world.py`. The reference below is generated
   from them (`python -m factory doc`); a test fails if it is stale.
2. **Shape is strict.** Unknown fields, repeated keys, repeated set elements,
   type coercion, non-UTC or sub-second times are all refused. Every
   categorical value is an enum.
3. **One event per act; consequences are derived.** A push ends the agent's
   hold and voids the previous push's open checks. A failed CI run voids the
   review. A merge unblocks what waited on it. None of these is logged again.
4. **Nothing is said twice.** A field that could disagree with the world does
   not exist. A push carries no model: the config says what each agent runs.
   A bug carries no "where found": the world knows what its finder was doing
   (holding an issue, reviewing, in a use session) and records it.
5. **Decisions and observations differ.** A decision (`taken`, `returned`,
   `published`) is an act whose record is the act: refusing it means it did not
   happen. An observation (`push`, `ci_done`, `merged`) reports something that
   happened outside: refusing it means the model and the world disagree. Every
   event declares which it is.
6. **The config is in the log.** `config_applied` carries all of it, so every
   line is checked against the policy it ran under. Agents are declared by
   type and count (three `claude-code`, two `grok`), and are named
   `claude-code-1`, `claude-code-2`, `grok-1` ….
7. **Nothing is edited.** A fact that can be wrong when first stated (which
   pull request introduced a bug) is restated by an event naming the one it
   replaces.
8. **Codes, then notes.** Analyses read reason codes; a free `note` sits
   beside some of them for the human.
9. **Legality is not policy.** The checker refuses the impossible. Whether an
   agent took the *best* issue is a question asked of a valid log.
10. **The simulation's hidden truth stays out.** Hidden bugs go elsewhere, so
    no analysis can use what the real factory could not see.

## A line

```json
{"schema":1,"seq":41,"t":"2026-11-25T21:04:09Z","actor":"claude-code-2",
 "event":"push","issue":17,"pr":388,"push":2,"sha":"4f1c…"}
```

The envelope is `schema`, `seq` (1, 2, 3 with no gaps), `t` (UTC to the
second, never before the line above) and `actor`: a role (`human`, `dictator`,
`watchdog`, `ci`, `reviewer`, `merger`, `pm`, `power_user`) or an agent of the
config in force. The rest is the event. The first line is `config_applied`.
Issues and pull requests share GitHub's numbers, so no number is used twice.

## Machines

### issue (one per issue)

A unit of work: enhancement, bug or friction. Waiting with a pull request means needs work.

Starts in `blocked`, `ready`.

- `parked` → `blocked`, `closed`, `ready`
- `blocked` → `closed`, `parked`, `ready`
- `ready` → `blocked`, `closed`, `held`, `parked`
- `held` → `blocked`, `checking`, `closed`, `parked`, `ready`
- `checking` → `blocked`, `closed`, `parked`, `ready`
- `closed` → (final)

### initiative (one per issue)

A larger goal, never worked on directly.

Starts in `open`.

- `open` → `closed`
- `closed` → (final)

### agent (one per agent)

One agent slot. Off while holding an issue means the issue is stale.

Starts in `off`.

- `off` → `idle`, `working`
- `idle` → `off`, `working`
- `working` → `idle`, `off`

### quota (one per agent)

Whether the agent's plan lets it run.

Starts in `ok`.

- `ok` → `out`
- `out` → `ok`

### ci (one per pr/push)

CI on one push.

Starts in `pending`.

- `pending` → `fail`, `pass`, `void`
- `pass` → (final)
- `fail` → (final)
- `void` → (final)

### review (one per pr/push/reviewer)

One reviewer of the config on one push.

Starts in `pending`.

- `pending` → `approved`, `changes`, `void`
- `approved` → (final)
- `changes` → (final)
- `void` → (final)

### pr (one per pr)

The one pull request of an issue.

Starts in `open`.

- `open` → `abandoned`, `merged`
- `merged` → (final)
- `abandoned` → (final)

### dictator (one)

The dictator acts only while ticking.

Starts in `resting`.

- `resting` → `ticking`
- `ticking` → `resting`

### version (one per version)

A release branch and its candidate builds.

Starts in `candidate`.

- `candidate` → `published`
- `published` → (final)

### use (one per use)

The human or the power user using one build.

Starts in `open`.

- `open` → `ended`
- `ended` → (final)
